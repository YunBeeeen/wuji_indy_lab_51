## 1. tip_link 프레임 불일치 (관측 버그)

`obs[40:55]`(손끝 5개)가 **잘못된 URDF**로 계산되고 있었다. 프로젝트에 Wuji URDF가
두 벌 있는데 `*_tip_link` 원점이 다르다.

| | 엄지 | 검지 | 중지 | 약지 | 소지 |
|---|---|---|---|---|---|
| 프레임 원점 차이 | **3.00 mm** | **0.70 mm** | 0.001 mm | 0.012 mm | 0.000 mm |

- 원인: `*_tip_fixed` origin z. 엄지 28.3(v1.0.2) vs 31.3 mm(신 릴리스), 검지 27.4 vs 26.7.
  로봇 이름부터 다르다 — `wujihand-right-v1.0.2` vs `wujihand-right`.
- **물리적 부품은 같은 자리에 있다.** 메시 원점이 반대로 상쇄해서 palm 좌표 부품
  centroid 차이는 검지 0.0003 mm, 엄지 0.33 mm. 즉 기하·접촉·pregrasp는 문제없고
  **틀린 건 관측 배선뿐**이었다 (`obs`는 부품이 아니라 링크 프레임 원점을 보고한다).
- 크기: 녹화 OPEN/CLOSE 한 사이클에서 엄지가 실제로 움직인 폭 12.92 mm 중 **3.01 mm
  (23.3%)**가 상수 바이어스.
- 왜 안 보였나: finger_reach는 중지만 쓰고(두 URDF가 0.001 mm로 일치) FK를 관측에서
  아예 뺐다.
- **USD 대조 완료(8/21 심야, 학습 종료 후):** `verify_tip_frames_isaac.py` 로
  `obs[40:55]` 를 두 URDF FK 와 대조 —
  `|Isaac − ISAAC_URDF| = 0.0001 mm`, `|Isaac − OFFICIAL_URDF| = 2.9981 mm`(엄지).
  USD 가 임포트 원본 URDF 와 일치하고, 선택이 맞았음을 확인. FK 사슬 3구간이
  전부 닫혔다: `USD ≡ 로컬 URDF(0.0001mm)` / `로컬 vs 공식(2.998mm)` /
  `공식 ≡ MuJoCo site(6.7e-08m)`.
- 조치: `obs[40:55]`를 백엔드가 아니라 `observation_adapter`가 q에서 FK로 푼다.
  `WujiHand1FingertipFK(source)`는 기본값 없음 — 어느 URDF인지 반드시 명시.
  부수 효과로 `WujiBackend`에서 `get_fingertip_positions_in_palm`이 빠졌고, 그게
  실물 백엔드를 막던 마지막 메서드였다.

## 2. `mujoco_deploy` → `Deploy` 재편

41개 파일을 층으로 나눴다. 기준은 "공유되는가"가 아니라 **"바꾸면 학습된 체크포인트가
무효가 되는가"**.

```
Deploy/
├── common/     정책 계약, tip FK, 스틱 포즈 수학, Isaac 리셋 상수, Protocol 2개
├── policy/     obs → action.  백엔드 중립
├── vision/     실측 리그, 시뮬 ArUco 픽스처, 사용자 트래커 3개, 브리지
├── backends/   mujoco_*  real_wuji*   (mujoco XOR wujihandpy)
├── run/        백엔드를 고르는 유일한 층 = 진입점 6개
├── models/     배포용 ONNX (학습 로그에서 복사)
└── assets/  tools/  tests/
```

임포트 방향 `run → backends → policy/vision → common`을 테스트로 강제했고, 재편 중
**역방향 의존 2건을 실제로 잡았다**: `make_finger_reach_backend`(policy에서 MuJoCo
백엔드 생성)와 Protocol 2개(`perception`/`backend_protocol`)의 위치.

옛 `scene_contract.py`는 Isaac 실측 상수와 시뮬 ArUco 픽스처가 섞여 있어
`common/isaac_reset.py` + `vision/sim_aruco.py`로 갈랐다.

## 3. 배포 리그 프레임 (`vision/deploy_rig.py`)

Vision 폴더의 실측값을 출처 표시와 함께 가져왔다. 검증된 것 4개(카메라 2대 외부
파라미터, `T_BASE_J6`, 마운트 오프셋), 미검증 2개.

- **마운트 요각 155°와 q6는 따로 검증 불가.** 같은 축 회전이고 마운트 이동도 그 축
  방향이라 `Rz(q6)@Rz(155) == Rz(q6+155)`가 4.6e-16으로 성립. 식별 가능한 건 합뿐.
- 사용자가 팜업 자세로 합을 확인 → **180.000097°**. 다만 눈으로는 178.4~187.0° 범위가
  다 "5° 이내 수평"으로 보인다. 팜업 최적은 182.724°이고 180을 쓰면 **3.73° 잔차
  (palm 100 mm 지점에서 6.5 mm)**. 최적값을 채택하지 않고 기록만 했다 — 잔차가 요각이
  아니라 `T_BASE_J6`(고정 q1~q5) 오차일 수도 있어서.
- `palm_link +X`가 팜 판 법선인 것을 메시로 확인: bbox `31.9 × 81.1 × 104.8 mm`,
  면적가중 면법선의 99.77%가 X축.

## 4. 비전 브리지 (`vision/provider.py`)

사용자 트래커 3개를 **한 줄도 안 고치고** 조립만 했다. `CameraStream` /
`StickTrackerState` / `CameraProcessingWorker` / `select_final_pose_for_stick`을
그대로 쓴다.

트래커의 `reason` → `PoseState` 사다리를 **시간 기준(ms)**으로 만들었다. 프레임 수로
하면 카메라가 15→30 Hz로 바뀔 때 임계값이 조용히 절반이 된다.

```
MAIN이 마커 하나라도 봄        → VALID
MAIN 둘 다 놓침 + SIDE 유효    → VALID (source=SIDE 기록)
둘 다 무효 ≤ 100 ms            → HOLD    정책 계속
둘 다 무효 100~250 ms          → STALE  ┐ safe_stop
둘 다 무효 > 250 ms            → LOST   ┘
```
100/250 ms는 **측정값이 아니다.** 이 파지가 얼린 포즈를 얼마나 견디는지 아직 안 쟀다.

## 5. 첫 105D 실물 read-only 실행 (실측)

카메라 2대 → 마커 → 스틱 7D → 105D 관측 → ONNX → 20D 목표. **150스텝 완주.**

### 30 Hz 유지 여부
```
예산 초과 1/150 틱 (0.7%)   late_by_ms = 1.33
total   평균 21.67 ms   p95 24.38   최대 34.49
```

### 단계별 (계측 완결, 미계상 0.04 ms)
```
joint_read   18.27 ms  p95 20.55   61.6%   ← 병목
observe       2.76      3.43       10.3%
command       0.52      0.69        2.1%
build         0.08      0.13        0.4%
```
`joint_read` 18.27 ms는 **read-only 전용**이다. 이 경로는 `realtime_controller`를 열지
않아 `self.controller is None` → `hand.read_joint_actual_position()`(블로킹 SDO)로
떨어진다. 주행 경로는 컨트롤러 스트림을 쓴다. **실제 주행 틱 추정 ≈ 3.4 ms (예산의 10%).**

### 인지 지연 (게이지)
```
main_frame_age_ms   평균 54.88   p95 82.18
main_tracker_ms     평균 27.36   p95 46.52
side_frame_age_ms   평균 49.36   p95 53.27
latest_pair_dt_ms   평균 10.51   p95 32.27
```
프레임 나이 ≈ 트래커 처리(27) + 비동기 오프셋(≤ 카메라 주기 33). **정상 동작의 결과이지
결함이 아니다.** Isaac에는 없던 sim-to-real 격차이므로, 파지가 이 지연을 견디는지는
Isaac에서 지연 주입으로 따로 재야 한다.

### 표준 트래커 대조 (사용자 실행)
```
MAIN capture 29.80 Hz | processed 29.80 Hz | proc_mean 30.0 ms | skipped 1
SIDE capture 30.00 Hz | processed 29.80 Hz | proc_mean 23.7 ms | skipped 1
```
**트래커는 30 Hz를 유지한다.** 통합본의 26~27 ms와 사실상 같아 재편으로 인한 저하는 없다.

### 리그 상태
SIDE 카메라는 현재 배치상 마커를 못 본다(의도됨). MAIN이 `[0,1,3]`을 보고 Stick2는
마커 3 하나로 도는데, 스틱당 마커 1개면 충분하므로 문제 아님.

## 6. 슬루 가드 오설정 (첫 실행에서 발견)

`--max-step-rad` 기본값 0.05 rad이 **계약의 관절별 액션 스케일(0.1/0.1/0.2/0.15)보다
작아** 합법 출력을 거부했다. `finger5_joint3`의 0.1326 rad는 정상이다. 4관절 reach
태스크(스칼라 0.1)에서 물려받은 값을 더 줄인 것이 원인. 가드를 관절별로 바꾸고 기본값을
`ACTION_SCALE_RAD`로 두었다 — 합법 출력에는 무동작, 손상된 ONNX·디코드 버그는 여전히 포착.

## 7. 그 외

- `safe_stop`을 **목표 동결**로 통일. disable도 아니고 측정 q 재래치도 아니다
  (`q_target - q`가 파지 preload라, 재래치하면 쥐는 힘이 사라진다). MuJoCo 판도 같이 고쳤다.
- `RealWujiHand`에 `health()` / `safe_stop()` 추가 → `WujiBackend` 충족.
- `run_hand_policy_real.py` 신설. `run_mujoco_policy.py`와 단계 1:1, RELEASE 자리가
  "젓가락 삽입 대기(온도 감시, 45초 제한)".
- `run_mujoco_policy.py` 신설 — glide → settle → 스틱 놓기 → 정책. 놓으면 MuJoCo는
  Stick1 92.3 mm / Stick2 108.8 mm로 낙하(기존 결론과 동일), `--release never`는 0.00 mm.
- 단계별 지연 계측(`common/timing.py`) 신설. 지속시간과 게이지를 분리하고 **미계상 시간을
  보고서가 직접 지적**한다.

# 2026-08-19 — Finger Reach 실물 배포, 첫 sim-to-real 비교

> 8월 18일 저녁부터 19일 새벽까지 이어진 작업. Isaac 학습/play와 실물 하드웨어 실행은
> 사용자가 했고, Claude는 배포 코드 작성과 로그 판독을 맡았다.
> 실물 SDK 함정은 `CLAUDE.md`의 "실물 Wuji Hand (wujihandpy)" 절에 따로 적었다.

## 1. 실물 백엔드 신설

`wujihandpy`로 실제 Wuji Hand에 finger_reach 정책을 올렸다. MuJoCo 경로는 건드리지
않았고 회귀 검사에서 CSV 최대차 `0.000e+00`(비트 단위 동일)을 매 변경마다 확인했다.

새 파일:
- `mujoco_deploy/real_wuji.py` — `RealWujiHand`. SDK 경계, (5,4)↔(20,) 변환,
  enable/disable, 전류 한계, slew 가드, IO 타이밍 측정
- `mujoco_deploy/real_wuji_scheduler.py` — 90 Hz 명령 루프 + 3틱마다 정책,
  `move_to_start_pose`, `glide_to_pose`
- `mujoco_deploy/run_finger_reach_real.py` — CLI, 단계별 진단 모드, CSV
- `mujoco_deploy/CLI.md` — 세 진입점 인자 정리

공유 계약(`finger_reach.py`, `policy_contract.py`, `onnx_policy.py`)은 두 백엔드가
그대로 쓴다. 관측·정규화·액션 디코딩이 한 벌뿐이라 갈라질 수 없다.

기존 파일 수정:
- `finger_reach.py` — `seed_from_current_state()` 신설, `reset()`이 이를 재사용.
  `command()`/`observe_after_hold()`에 `q_all` 주입 인자 추가(기본값 None이라
  MuJoCo 동작 불변)
- `onnx_policy.py` — 차원을 **필수 인자**로. 105D/20D 기본값이 남아 있으면
  reach 정책을 못 읽고, 어느 한쪽이 "진짜 계약"이 되어버린다
- `policy_contract.py` — `HAND_JOINT_COUNT` 분리. `ACTION_DIM=20`이 "손에 관절이
  20개"와 "파지 정책 출력이 20D" 두 뜻으로 쓰이고 있었다

## 2. 실물 기동 순서와 검증 결과

`--read-only` → `--measure-timing` → `--hold-middle` → `--test-middle-joint 1~4`
→ `--zero-policy` → `--policy` 순으로 올렸다.

- **관절 매핑 확정**: J1~J4 네 개 다 `MATCHES`. 다른 관절 이동은 0.008 rad 이하
  (엔코더 노이즈). canonical `finger3_jointN` ↔ 하드웨어 중지 J(N)
- **타이밍**: 명령 주기 평균 11.05~11.10 ms(목표 11.111), 총 8201틱 중 늦은 틱 1개
  (0.012%). 정책 주기 평균 33.3334 ms, 40초 주행에 누적 드리프트 +0.0001 s
- **정책 스텝 비용**: 평균 0.75 ms (예산 33.3 ms의 2.3%)

## 3. 첫 sim-to-real 비교

같은 시각·같은 시나리오·같은 ONNX로 MuJoCo와 실물이 각자 정책을 돌렸다
(`--parallel-mujoco`, 상태 복사가 아니라 독립 루프).

관절 각도 차이 (정착 구간):

| joint | 차이 |
|---|---|
| finger3_joint1 | 135.0 mrad = 7.73° |
| finger3_joint2 | 9.7 mrad = 0.56° |
| finger3_joint3 | 73.2 mrad = 4.19° |
| finger3_joint4 | 81.6 mrad = 4.68° |

**타깃당 5초 → 10초로 늘려도 그대로였다** (J1 135.8 → 135.0 mrad). 실물이 3~4초에
정착하고 그 자리에 머문다. LowPass 지연이 아니라 정상상태 차이다.

부하가 큰 관절일수록 차이가 크다. J2만 0.56°인데 이 관절은 0.11~0.23 rad 범위만
쓰고 부하가 가장 작다. 서보 게인 부족의 서명으로 보이나 마찰과 아직 못 가렸다.

**손끝 기준으로는 결론이 뒤집힌다**: 실물 q에 URDF FK를 걸어 목표까지 거리를 재면
실물 4.64 mm vs MuJoCo 8.68 mm로 **실물이 더 정확하다.** 중지는 4 자유도로 3차원
목표를 쫓아 여유자유도가 1개이고, 두 플랜트가 서로 다른 널 스페이스 가지에 앉은
것이다. 관절 4~8도 차이는 태스크 성능 차이가 아니었다.

단 이 4.64 mm는 **기구학 모델 출력**이지 측정이 아니다. 링크 길이와 엔코더 영점이
URDF와 같다는 가정이 깔려 있고, 축별 오차가 `x: +4.03 mm` 한 축에 몰린 계통 편향이라
영점 오프셋 가능성이 있다. 외부 측정 전까지 "모델 기준"이라고 붙여야 한다.

## 4. 실물 전용으로 설계한 것들

- **teleport 없음**: 시뮬 reset을 `move_to_start_pose`로 대체. 중지 4개만 시뮬
  시작 자세를 고정 타깃으로 잡고 90 Hz로 재전송, 엔코더로 도착 확인 후
  `stable_seconds` 유지. 나머지 16관절은 실측값 유지(enable도 안 된 관절에
  시뮬 자세를 명령하지 않기 위해)
- **복귀는 선형**: 고정 타깃 + 필터는 지수형이라 초기 속도가 Δ/τ다. 1.18 rad
  복귀에서 3.7 rad/s가 나와 놀랐다(정책 최대 3 rad/s보다 빠름). `glide_to_pose`로
  목표를 3초에 걸쳐 선형 이동 → 0.39 rad/s
- **90 Hz 진단 로깅**(`--log-commands`): 정책은 30 Hz 샘플만 쓰되 기록만 조밀하게.
  관측 히스토리가 "정책 스텝 하나 간격의 두 샘플"로 정의돼 있어 정책 샘플링 주기는
  바꿀 수 없지만, 읽기 비용이 0.009 ms라 로깅은 사실상 공짜다

## 5. LowPass 실측

`τ = 1/(2πf)` 모델이 정확히 맞았다. 0.5 Hz에서 0.03 rad 스텝의 0.5초 후 응답이
**79.4%**로 관측됐고 예측치는 79.2%다. 덕분에 정착 시간을 계산으로 예측할 수 있다.

| cutoff | τ | 정책 한 스텝(33.3 ms)에 반영되는 비율 |
|---|---|---|
| 0.5 Hz | 318 ms | 9.9% |
| 2.0 Hz | 80 ms | 34.2% |

시뮬에는 이 필터가 없다. 실물에만 있는 플랜트 요소이므로 비교 시 감안해야 한다.

## 6. 미확인으로 남긴 것

- **보내는 게 실제로 90 Hz인지** — 확인된 건 파이썬이 API를 초당 90번 호출했다는
  것뿐이다. `set_joint_target_position`이 0.039 ms로 끝나는 걸 보면 realtime
  스트림에 큐잉만 하고 리턴하는 것으로 보인다. SDK의 `start_latency_test()` /
  `stop_latency_test()`로 확인 가능
- **펌웨어 서보 게인** — `wujihandpy`에 Kp/Kd 설정 API가 없다. 위치 명령과
  LowPass 필터만 노출된다. `real_wuji.py`는 어떤 게인도 설정하지 않으며 이를
  주석에 명시했다
- **기구학 검증** — 링크 길이·엔코더 영점이 URDF와 같은지 미측정
- **FK 손끝 오차와 관절별 분해가 코드에 없다** — `compare_reach_logs.py`는 전체
  평균/최대만 낸다. 이번 결론의 근거인 분석은 전부 셸 임시 코드였다

## 7. 시작 자세 이동도 선형으로 (오후)

복귀만 선형이고 **나가는 이동은 고정 타깃 + 필터(지수형)**로 남아 있었다. 시작
자세가 현재 자세와 가깝다는 전제였고 실제로 0.04 rad 수준이라 문제가 없었다.

주행이 중간에 끊겨 손가락이 굽은 채 남으면서 그 전제가 깨졌다. 변위가 40배
커지니 같은 방식의 초기 속도가 `Δ/τ`로 폭증한다.

| 방식 | 1.68 rad에서 초기 속도 |
|---|---|
| 고정 타깃 + LowPass 2.0 Hz | 21.11 rad/s |
| 고정 타깃 + LowPass 0.5 Hz | 5.28 rad/s |
| **선형 glide 3초** | **0.56 rad/s** |

`run_finger_reach_real.py`의 시작 이동을 `move_to_start_pose` → `glide_to_pose`로
바꾸고 `--start-seconds`(기본 3.0)를 추가했다. 지난 스펙의 "시작 자세는 고정
타깃으로"를 사용자 요청으로 뒤집은 것이라 코드 주석에 경위를 남겼다.
`--test-middle-joint`는 0.03 rad짜리 작은 스텝이라 `move_to_start_pose`를 유지한다.

실측(run 5) 시작 이동의 0.33초당 오차 감소:

```
0.110 → 0.207 → 0.191 → 0.191 → 0.192 → 0.188 → 0.181 → 0.183 → 0.189 → 0.033
        └────────────── 등속 0.19 rad/0.33s = 0.57 rad/s ──────────────┘
```

예측 `1.6678/3 = 0.556 rad/s`와 일치. 첫 구간만 작은 것은 필터가 물리기까지의
지연이다.

### 같이 고친 두 가지

- **궤적 끝점 clamp** (`real_wuji_scheduler.py`) — 기계적 스톱에 눌린 관절은
  소프트 한계를 **넘겨서 읽힌다**(측정 `1.6804522` vs 상한 `1.680047`, 초과
  0.4 mrad = 0.023°). `glide_to_pose`가 측정값에서 보간을 시작해 첫 목표가
  범위 밖이 되어 `ValueError`로 죽었다. 시작점·목표점을 명령 범위로 clamp.
  관측·잔차에 쓰는 `q`는 원본 그대로이고, `write_joint_position_targets`의
  거부 정책도 유지한다 — clamp는 **궤적 생성에만** 적용된다.
- **복귀 실패 시 로그 보존** — CSV 쓰기가 try/finally 밖에 있어 위 크래시로
  20초 주행 데이터가 통째로 날아갔다. 복귀를 try/except로 감쌌다.

## 9. 명령 여백 0.95 도입

### 도달성 손실이 없음을 먼저 확인

19만 점 격자 + 국소 정밀화 IK (중지 4관절 체인만 뽑아 Rodrigues로 벡터화):

| factor | 실행한 4목표 최소오차 | REACH 박스 2000점 5 mm 이내 |
|---|---|---|
| 1.00 | 전부 0.000 mm | 100.0% |
| **0.95** | **전부 0.000 mm** | **100.0%** |
| 0.90 | 최대 0.001 mm | 100.0% |

**여백이 도달 범위를 깎지 않는다.** 4 DoF로 3D 목표를 쫓아 여유자유도가 1개라
한계 근처 해를 버려도 다른 자세로 같은 지점에 간다. 즉 J3가 눌리는 것은
기구학적 필연이 아니라 **정책이 고른 자세**다.

### 정의

`0.95 × 상한`이 아니라 **중심 ± 0.95 × 반범위**. Isaac의
`soft_joint_pos_limit_factor`와 같은 정의다(음수 하한에서 뜻이 뒤집히지 않고,
나중에 `assets/wuji.py:95`로 옮겨도 같은 값이 된다).

```
J1 [-0.2488, +1.5578]   상한 47.5 mrad (2.72°) 낮춤
J2 [-0.3984, +0.3984]        21.0 mrad (1.20°)
J3 [-0.4899, +1.6244]        55.6 mrad (3.19°)   ← 문제 관절
J4 [-0.4935, +1.6280]        55.8 mrad (3.20°)
```

### 계약 테이블은 미변경

`COMMAND_TARGET_LIMITS`를 줄이지 않고 `soft_command_limits(fraction)`이 **새
테이블을 반환**한다. `policy_contract.py`의
`COMMAND_TARGET_LIMITS == OBSERVATION_NORMALIZATION_LIMITS` 검증은 "Isaac이 이
범위로 학습했다"는 사실의 기록이고, 여백은 그 위에 얹는 배포 판단이다. 이렇게
분리해야 **"실물만 0.95"라는 불일치가 이름을 갖고 드러난다.** 정규화 테이블은
손대지 않았다(건드리면 정책 입력 매핑이 깨진다).

`decode_reach_action`의 `raw_action`/`clipped_action`/`unclamped_target`도 그대로
둔다 — 정책이 무엇을 요구했는지의 기록을 안전 클램프가 지우면 안 된다.
바뀌는 건 `position_target` 하나다.

### MuJoCo 실측 효과

| | J3 상한 5 mrad 이내 | 지문 오차 평균 |
|---|---|---|
| MuJoCo 1.00 | 80.4% | 8.80 mm |
| MuJoCo 0.95 | **0.0%** | **8.17 mm** (−0.62) |

스톱 압착이 사라지고 오차는 오히려 줄었다. 네 목표 전부 −0.60~−0.64 mm로
일관되어 우연이 아니다.

### 기본값

| CLI | 기본 | 이유 |
|---|---|---|
| `run_finger_reach_real` | **0.95** | 실물 보호 |
| `run_finger_reach` (MuJoCo) | **1.0** | 기존 로그 재현성 |

변경 전 코드와 변경 후 기본값의 MuJoCo CSV가 시각 컬럼 제외 **완전 동일**함을
확인했다. 이를 보장하려고 `fraction == 1.0`은 재계산하지 않고 원본을 복사한다
(float32 재구성은 1 ULP 어긋나 bit-identical이 깨진다 — 테스트가 실제로 잡았다).

두 기본값이 다르면 짝지은 비교가 조용히 어긋나므로 **`--parallel-mujoco`가 실물
쪽 값을 자식 프로세스에 자동 전달**한다.

적용 범위: 정책 클램프, 붙잡아 두는 16관절, 시작 glide, 복귀 glide, 단일 관절
진단. `real_wuji.write_joint_position_targets`의 하드 계약 검사는 그대로 둬서
여전히 진짜 버그만 잡는다.

| 파일 | 변경 |
|---|---|
| `mujoco_deploy/policy_contract.py` | `soft_command_limits(fraction, limits=None)` 신설 |

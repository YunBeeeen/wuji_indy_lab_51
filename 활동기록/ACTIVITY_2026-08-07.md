## 3. 신규 보상 항 — `stick_axis_lateral`

### 배경: 젓가락이 "옆으로 벌어지는" 문제

좌표축 명명을 확정했다 (stick2 로컬 프레임, 정규직교 3축):

| 표현 | 이름 | 벡터 | 지표 |
|---|---|---|---|
| 스틱 방향(장축) | axial | `(0,1,0)` | `tip_axial_error` |
| 위아래로 맞닿는 방향(개폐) | separation | `ref = (0.888, 0, −0.460)` | `tip_surface_gap` |
| **옆으로 벌어지는 방향** | **lateral** | `n = (0.460, 0, 0.888)` | 아래 두 개 |

lateral은 **두 개로 나뉜다** — 3D에서 두 직선이 만나려면 위치와 방향이 둘 다 맞아야
한다.

```
lateral 위치 : 팁 두 점의 n 성분  → tip_lateral_error        (보상 있었음)
lateral 방향 : stick1 축의 n 성분 → stick_axis_skew_angle    (아무도 안 봤음)
```

`_tip_geometry_from_palm_poses`는 **stick1의 샤프트 축을 계산조차 하지 않는다.**
그래서 스틱이 기운 채로 닫혀 맞물리지 못하고 미끄러졌다.

### 실측 (항 도입 전, `hand_move` it 7402)
```
stick_axis_skew_angle   mean 3.05°   min 2.50°   ← 한 번도 0 근처로 안 감 = 상시 편향
OPEN 5.31° / CLOSE 5.28°                        ← 모드 무관
reset(pose_005)         5.21~5.72°
```

### 설계
```python
stick_axis_lateral = RewTerm(
    func=hand_grasp_mdp.stick_axis_lateral_alignment,
    weight=10.0,
    params={..., "sigma": 0.05},   # 0.05 rad = 2.9°
)
```
- `exp(−skew/σ)`, **모드 게이트 없음** (상시 편향이고 이미 기운 채 들어오면 CLOSE에서
  못 고침)
- 기존 지수에 넣지 않고 **별도 덧셈 항**. `mode_tip_gap_tracking`은 gap/lateral/axial을
  한 지수에 곱해 넣으므로, 거기 얹으면 skew가 나쁠 때 gap gradient까지 깎인다.
- **면내각(개폐 자유도)에 gradient 0**임을 수치로 검증 (면내 −10°~+10°에서 보상 동일).

목표를 0으로 둔 근거: pose_005는 *젓가락을 쥐는 것*을 검증한 자세이지 *팁으로 무는
것*은 검증한 적이 없고, 기준 방향 자체가 그 자세의 **팁 위치**에서 뽑혀 축에 대해서는
아무 것도 보장하지 않는다. 정책도 시키지 않았는데 5.2° → 3.05°로 내려갔다.

### 효과
```
stick_axis_skew_angle  min :  2.50° (항 없음) → 0.30° (1단계) → 0.05° (2단계)
```
항이 없을 때는 전 구간에서 2.5° 아래로 한 번도 안 내려갔다. mean이 따라오는지가 관건.

`HandMoveRewardsCfg`에 넣었으므로 **hand_move + hand_object(상속)**에 적용된다.
`hand_grasp`는 미적용.

## 6. `cube_hold` 가 0인 진짜 원인 — 각속도 항이 솔버 노이즈를 벌주고 있었다

### 게이트 메트릭 신설
`cube_distance_to_stick2_tip` / `*_speed_rel` 은 게이트가 없어 접근·회전 구간(0.5~2.0 s)
을 포함한다. 그 구간엔 큐브가 기둥 위에 가만히 있어도 Stick2 가 움직이므로 **상대** 속도가
크게 잡힌다. `holding`(= retracted × 양쪽 힘 > 0)으로 게이트한 3종을 추가했다.

`hold_distance`, `hold_linear_speed`, `hold_angular_speed` — 조건부 정규화(게이트가 켜져
있던 시간으로 나눔)까지 포함. 수치 검증: 3초 미파지 + 2초 파지(13mm) 시나리오에서
희석식 5.20 mm(틀림) vs 조건부 13.00 mm(참값).

### 실측 결과 (run `2026-08-07_16-36-33`, it 202)

```
                     게이트 없음    파지 중(게이트)
hold_distance          93.3 mm        8.07 mm     <- 11배 오염돼 있었음
hold_linear_speed      0.085 m/s      0.040 m/s   <- 절반
hold_angular_speed     10.25 rad/s   10.43 rad/s  <- 거의 동일
```

stability 분해:
```
거리    8.07 mm    -> 지수  0.81
선속도  0.040 m/s  -> 지수  0.80
각속도  10.43 rad/s-> 지수 10.43     <- 전체의 87%
                      합 12.04  ->  stability = 6e-6
```

### 이전 진단 3건 정정

1. **"13.1 mm 라 팁이 아니라 샤프트 안쪽에서 물고 있다"** → 실제 **8.07 mm**(max 8.60,
   편차 0.5 mm). 기하 예측(면-정면 6.0 / roll 20.6°에서 7.0 mm)에 근접. **큐브는 팁에
   제대로 물려 있다.** 13.1 mm 는 에피소드 전체 min 이라 접근 구간이 섞인 값이었다.
2. **"각속도 9.98 은 접근 구간 오염일 것"** → 게이트를 걸어도 10.43. 오염이 아니다.
3. **"선속도 항 하나에 이미 막힌다"** → 게이트하면 지수 0.80, 안 막힌다. 이 판단은
   내가 스스로 "오염됐다"고 지적한 값으로 낸 결론이었다(사용자 지적).

### 각속도 10.43 rad/s 는 회전이 아니라 노이즈다

- 큐브 5 mm / 3 g → `I = m·a²/6 = 1.25e-8 kg·m²`. 0.07 N 이 반폭 2.5 mm 에 편심으로
  걸리면 `α = 14,000 rad/s²`, **물리 스텝(1/120 s) 한 번에 117 rad/s**. 10 rad/s 는
  이 크기 물체의 노이즈 바닥이다.
- 지표가 `norm(ω_cube − ω_stick2)` 이라 항상 양수다. **알짜 회전 0 인 진동도 평균이
  10 으로 찍힌다.** "얼마나 도는가"가 아니라 "얼마나 떠는가"를 재고 있었다.
- `hold_distance` 편차가 0.5 mm 뿐이다. 초당 1.7 바퀴 도는 큐브라면 정사각 단면이
  면↔모서리로 바뀌며 팁 간격이 41% 출렁여야 한다. 단단히 물려 안 움직인다는 뜻.

### 조치 — 각속도 항 제거

`cube_hold` 와 `cube_relative_stability` **둘 다**에서 `- angular_speed / angular_speed_sigma`
제거. 파라미터도 시그니처에서 삭제(cfg 가 넘기지 않는 것 확인).

**곱셈 항에 정책이 못 줄이는 양을 넣는 것은 σ 오설정보다 나쁘다** — 다른 게 아무리
좋아져도 목표가 0 에 붙어 있다. `linear_speed` 는 유지(지수 0.80, 정상 스케일이고
미끄러짐이야말로 큐브를 놓치는 실제 원인).

두 항 모두에서 빼는 이유: 한쪽만 빼면 "큐브가 안정적이다"가 같은 상태를 기술하는 두
보상에서 서로 다른 뜻이 된다.

### 예상 효과 (weight·distance·σ 전부 그대로)

```
stability = exp(-0.807 - 0.804) = 0.200
cube_hold = 0.386(holding) × 1.0(force) × 0.200 × 200 × 9s  ≈ 139 점   (현재 0.084)
cube_relative_stability                                      ≈  39 점   (현재 0.021)
```
`holding` 이 0.386 → 0.9 로 오르면 `cube_hold` 는 자동으로 323 점이 된다.

### 검토했다가 안 한 것

- **거리 기준점 0 → 6 mm**: `exp(-d/σ)` 는 d=0 에서 최대라 "이상적인 거리 = 0"을
  요구하는데, 스틱 반두께 3.5 + 큐브 반폭 2.5 = **6.0 mm 가 물리적 하한**이다. 완벽한
  파지도 `exp(-0.6) = 0.55` 가 천장. 원리적으로 틀렸지만 **효과가 일률적으로 1.822배뿐**
  이라(0.084 → 0.153) 각속도를 안 고치면 무의미했다. 각속도 제거 후에는 거리 항이
  `exp(-0.807) = 0.446` 으로 의미 있는 판별자가 되므로 급하지 않다. 실측 8.07 mm 를
  확보했으니 나중에 근거 있게 바꿀 수 있다.
- **ref 를 실측값 8 mm 로**: 현재 자세를 정답으로 고정해 gradient 가 0 이 된다. 6 mm 로
  두면 23% 여지가 남고, 그걸 메우려면 roll 을 면-정면으로 돌려야 해서 **지금 아무도 안
  보는 자유도에 간접 압력**이 생긴다.
- **`cube_hold` weight 200 → 50**: 속도 두 항을 다 빼면 565 점이 되어 에피소드 총 보상
  (533)을 넘기므로 필요했으나, **각속도만 빼면 139 점**이라 그대로 둘 수 있다.
- **`angular_speed_sigma` 1.0 → 30 으로 완화**(항 유지): 되돌리기 쉽고 런 기록에 남는
  장점이 있었으나, 사용자 판단으로 삭제를 택함("각속도는 필요 없다, 선속도만 보면 된다").

## 7. (추가 기록) lateral 독립 항 + clamp 해제

`hand_move` 에서 스틱이 CLOSE 때 **교차**하는 증상을 추적한 결과.

### 진단
```
tip_lateral_error 9.14 mm   vs   스틱 단면 7 mm
```
옆으로 어긋난 양이 두께를 넘어 **두 단면이 겹치는 부분이 없다.** 닫으면 만나는 게
아니라 서로 지나간다.

보상이 못 막는 이유가 두 겹이었다.
```python
surface_gap = clamp(transverse_distance - support1 - support2, min=0.0)
```
1. `transverse_distance` 가 **norm** 이라 "옆으로 9mm" 와 "개폐 방향으로 9mm" 를 구분
   못 한다.
2. `clamp(min=0)` 이 음수를 전부 0 으로 모으는데, `CLOSE_TIP_GAP = 0` 이라 **그 0 이
   목표값**이다. 서로 다른 상태가 전부 만점으로 붙는다.

실제로 roll 20.6 deg 에서 support 합이 9.02mm 라, lateral 9.02mm 인 완전 교차가
`surface_gap = 0` = **완벽한 CLOSE** 로 보고된다.

### 조치
```
mdp.py  _tip_geometry_from_palm_poses(..., clamp_gap=True)      파라미터 신설
        mode_tip_gap_tracking(..., lateral_sigma=None 가능, clamp_gap)
        mode_grasp_stability(...  동일)
        _tip_surface_gap_and_lateral_error(..., clamp_gap)
        OpenCloseModeHeld(..., clamp_gap)
        tip_lateral_alignment()                                 신규 보상 함수

hand_move_env_cfg.py  tip_lateral  w15, sigma=TIP_LATERAL_SIGMA(5mm), 모드 게이트 없음
                      open/close_tip_gap, mode_grasp_stability -> lateral_sigma=None
                      success 보상/종료 -> clamp_gap=False (보상과 같은 정의)
managers.py           메트릭은 clamp_gap=False 로 통일 (부호 있는 값이 진단에 유용)
```
기본값은 전부 기존 동작이라 `hand_grasp` / `hand_setting` / `finger_reach` 무영향.

### 한계 (실측으로 확인)
- `clamp_gap=False` 는 **부분 교차(lateral 2~7mm)에서만** 걸린다. 완전 교차
  (lateral ~= support 합)는 raw gap 이 애초에 음수가 아니라 그대로 만점이다.
- 그 구간을 잡는 건 `tip_lateral` 독립 항 하나뿐이다.
- 근본 수정(`transverse_distance` 를 ref 성분 투영으로)은 **미적용**. 정상 기하에서는
  두 정의 차이가 0.29mm 뿐이라 기존 보정값은 그대로 유효하다.
- `hand_object` 실측에서 `tip_surface_gap` min 14.8mm — **음수가 한 번도 안 나왔다.**
  clamp 해제가 수치 특이점을 드러낸다는 우려는 근거 없음.

## 8. (정정) `Episode_Reward` 는 합계가 아니라 초당 평균

```python
# managers.py:2056, IsaacLab reward_manager.py:120 과 동일
extras["Episode_Reward/" + name] = episodic_sum_avg / self._env.max_episode_length_s
```

이 세션 내내 예산을 `weight x 활성초` 로 계산했는데, **episode_length_s 배 부풀려진
값**이었다 (hand_move 15초 -> 15배).

올바른 최대치는 `weight x (그 항이 활성인 시간 비율)`.

정정 후 표 (hand_move it 752):
| term | w | max | 실측 | 달성률 |
|---|---:|---:|---:|---:|
| `mode_grasp_stability` | 50 | 50.00 | 0.50 | 1.0% |
| `functional_contact_min` | 20 | 20.00 | 11.99 | **59.9%** |
| `stick2_reference_pose` | 15 | 15.00 | 3.16 | 21.0% |
| `close_tip_gap` | 20 | 13.34 | 4.23 | 31.7% |
| `stick1_pivot` | 10 | 10.00 | 5.86 | 58.6% |
| `stick_axis_lateral` | 10 | 10.00 | 1.13 | 11.3% |
| `open_tip_gap` | 20 | 6.66 | 0.37 | 5.5% |
| `joint_reference` | 2 | 2.00 | 0.19 | 9.7% |
| | | **127.0** | **27.42** | 21.6% |

이 정정으로 뒤집힌 결론 둘:
1. "파지가 예산의 4% 만 번다" -> 실제 **60%**. `full_contact` 0.62 와 정확히 일치.

   지켜라" 라고 말하고 있었고, 정책은 선택적으로 버린 게 아니라 **유지에 실패**한
   것이었다.

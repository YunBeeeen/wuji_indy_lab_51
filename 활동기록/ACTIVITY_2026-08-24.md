## 1. glide 첫 목표가 백엔드에 거부됨 — float32 1 ULP

`Deploy/backends/real_wuji_scheduler.py` (02:21)

```
ValueError: joint target outside command limits
```

`glide_to_pose` 가 `q_start → q_goal` 을 선형 보간하는데, **`q_start == q_goal ==
upper` 인 관절**에서 float32 곱셈·덧셈이 상한을 1 ULP 넘겼다. 수학적으로는
`(1-α)·u + α·u = u` 지만 float32 에서는 아니다. 백엔드의 하드 계약 검사가 이걸
정확히 잡아 주행이 시작도 못 하고 죽었다.

**0.95 명령 여백을 넣은 뒤부터 일상적으로 발생한다** — pregrasp 의 여러 관절이
새 상한에 딱 붙게 됐기 때문이다.

```python
blended = (1.0 - alpha) * q_start.astype(np.float64) + alpha * q_goal.astype(np.float64)
self.backend.write_joint_position_targets(
    np.clip(blended, lower, upper).astype(np.float32), max_step_rad=allowance)
```

float64 로 섞고 **매 샘플 clip** 한다. 회귀 방지는 `GlideStaysInsideCommandLimitsTests`
+ float32 로 하면 실제로 넘친다는 것을 증명하는 메타 테스트 (안 그러면 이 테스트가
아무것도 안 지키면서 통과한다).

## 2. `current_sum += magnitude` — 클로저 재바인딩

`Deploy/run/run_hand_policy_real.py`

중첩 함수 안에서 바깥 이름에 `+=` 를 쓰면 파이썬이 그 이름을 **로컬로 재바인딩**해서
`UnboundLocalError` 가 난다. ENABLE 확인 + 젓가락 45초 삽입을 마친 **step 0 에서**
주행이 죽었다. 손을 다시 세팅해야 하는, 가장 비싼 시점의 실패다.

`current_sum[:] += magnitude` 로 고치고, 회귀 방지는 **AST 스캔**으로 넣었다 —
`on_policy_tick` / `on_hold_tick` / `report_move` 안에서 바깥 이름에 bare `+=` 가
있으면 테스트가 실패한다.

## 3. 전류 상한

### 구조 (사용자 질문에 대한 답)

*"1.2가 계속 되면 1.5A 까지 올라가는 건 아냐? 무조건 1.2A 에 막히게끔 알아서 힘을
조절함?"*

`write_current_limit` 은 **전류 루프 안의 클램프**지 레귤레이터가 아니다. 정책이
아무리 큰 위치 오차를 만들어도 전류는 상한에서 잘린다. 손이 힘을 "조절"하는 게
아니라 **못 넘게 자르는** 것이다. 열은 `I²`, 파지력은 `I` 에 비례하므로 상한을
내리면 열은 제곱으로, 힘은 선형으로 준다.

### 계측 구멍 먼저

`SATURATION_A = 1.49` 가 하드코딩이라 `--current-limit 1.2` 로 돌리면 **포화 탐지가
장님**이 된다(1.2 에 붙어 있어도 1.49 미만이라 0% 로 보고). `saturation_threshold(backend)`
를 넣어 **장치에서 읽어온 실제 상한 × 0.99** 를 쓴다. `--current-limit` 인자가 아니라
readback 을 쓰는 이유는 장치가 요청값을 그대로 받아준다는 보장이 없어서다.

`Deploy/run/run_temperature_probe.py` (신설, read-only) — 모터를 켜지도 목표를 쓰지도
않고 wujihandpy 온도 API 의 지연만 잰다. unchecked API 는 완료 토큰이 없어 **연속된
같은 온도값으로는 캐시가 언제 갱신됐는지 증명할 수 없다** — async 완료 지연이 유일하게
믿을 수 있는 측정이다.

### 실측

| 상한 | 로그 | 결과 |
|---|---|---|
| 1.5 A (기본) | `real_r96.csv` 162틱 | 틱당 3.7 관절이 1.48 A 이상. 20초를 못 감 |
| 1.3 A | 주행 로그 | 종료 최고 **76.3 °C**, **+29.5 °C / 30.0 s = +0.98 °C/s**, 틱당 평균 **5.4** 관절 포화. **평형 없음** |
| 0.8 A | `real_4500_i13.csv` 609틱 (20.3 s) | 틱당 평균 **6.26** 관절 포화, 최대 9, 한 번이라도 포화한 관절 **10/20** |

0.8 A 에서 포화 지속 시간이 긴 관절:

| 관절 | 포화 틱 비율 |
|---|---|
| `finger1_joint2` | 97.9% |
| `finger2_joint2` | 97.9% |
| `finger5_joint2` | 94.6% |
| `finger4_joint2` | 84.4% |

**결론: 상한을 낮춰도 duty cycle 은 안 줄어든다.** 포화한 관절 수는 오히려 늘었다
(5.4 → 6.26). 상한이 낮을수록 같은 위치 오차가 더 쉽게 천장에 닿기 때문이다.
열 예산이 늘어나는 건 `I²` 덕분이지 포화가 줄어서가 아니다.

### 내 오진 정정

앞서 *"1.2 A 는 49.5 °C 에서 평형이니 무한정 안전"* 이라고 한 것은 **틀렸다.**
그건 **무부하 스톨** 값이었고 파지 부하를 전혀 대표하지 못한다. 부하가 걸린 1.3 A
주행은 30초 동안 평형 없이 +0.98 °C/s 로 계속 올랐다.

## 7. 로그에서 체크포인트 역추적

실물 `--out` CSV 에는 **정책 경로가 안 적힌다.** 그래서 기록된 obs 를 후보 ONNX 에
통과시켜(L1) 역으로 찾았다. 정책은 결정적 함수라 일치하면 그게 그 체크포인트다.

| CSV | max\|diff\| | 정책 |
|---|---|---|
| `real_r95.csv` | 0.000e+00 | `hand_real/2026-08-18_23-57-25` model_4500 |
| `real_r96.csv` | 0.000e+00 | 〃 |
| `real_4500_i13.csv` | 0.000e+00 | 〃 |
| `real_2400.csv` | 0.000e+00 | `hand_real/2026-08-24_09-29-55` model_2400 |

차점 후보는 전부 0.6~0.8 이라 애매한 구석이 없다.

녹화 재생 쪽(`run_joint_replay`)은 사이드카가 있다 —
`joint_record_2026-08-20_00-34-12.meta.json` 의 `"checkpoint"` 가
`hand_real/2026-08-18_23-57-25/model_4500.pt`. 루트 `replay_mujoco.csv` 가 이 파일을
MuJoCo 로 되감은 출력이고, 시간 정렬 후 20관절 중 17개가 `max|diff| = 0.00000`.
나머지 3개(`finger2_joint4`, `finger5_joint3`, `finger1_joint4`)는 재생 쪽이
**1.627228975 로 상수 고정** — 당시 걸린 상한값인데 어느 표였는지는 안 남아 있다.

같이 있는 `joint_record_2026-08-20_00-23-19.csv` 는 **메타가 없고 구 포맷(26컬럼,
`qt_*` 없음)** 이라 재생도 못 하고 체크포인트도 증명 못 한다.
